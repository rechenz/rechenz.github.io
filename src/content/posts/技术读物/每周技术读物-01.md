## 1. 系统性的着色器削减：把《堡垒之夜》的着色器砍掉 68%

### 出处

- **原始演讲**：*Systemic Shader Reduction: How We Cut Fortnite's Shaders by 68%*，**Unreal Fest Chicago 2026**，Epic Games（工程侧 Jason Nadro / 内容侧 John Loff）
- **中文整理**：知乎作者「洛桑」，2026-07-29 发布 → [原始整理帖](https://zhuanlan.zhihu.com/p/2065857760663704678)
- **带全图的镜像版**：[gerigory.github.io](https://gerigory.github.io/UnrealFest2026-%E7%B3%BB%E7%BB%9F%E6%80%A7%E7%9A%84%E7%9D%80%E8%89%B2%E5%99%A8%E5%89%8A%E5%87%8F-%E5%A6%82%E4%BD%95%E6%8A%8A-%E5%A0%A1%E5%9E%92%E4%B9%8B%E5%A4%9C-%E7%9A%84%E7%9D%80%E8%89%B2%E5%99%A8%E7%A0%8D%E6%8E%89-68/)
- **类型**：二手整理笔记（视频关键帧截图 + 讲者原话转述），技术细节以 UE 5.8 官方文档为准
- **语言**：中文

### 为什么值得读

因为它讲的不是「调哪个 CVar 能涨帧」，而是**把着色器排列当成一个组合数学问题来建模，然后系统性收敛**。工程侧砍幂、内容侧砍底数，两条腿配合，半年内把 PC 端着色器从 **190 万 / 14 GB 压到 62 万 / 4 GB**——数量 −68%，体积接近 −70%。

对使用 UE5 且材质/外观体量大的项目（尤其 live service），这篇基本是照着抄都行的治理手册。

### 三个关键点

**一、心智模型**

```
着色器总量 = 材质 × 顶点工厂类型 × 着色器类型 ×（质量级别 / Shader Model）
```

引擎里着色器类型 155 种、顶点工厂类型 30 种。这个排列网格其实是**稀疏的**，`ShouldCompilePermutation()` 决定哪些格子真正激活——这是剔排列的最大杠杆。

**二、乘法爆炸的两个来源**

- **usage flag（使用标记）**对应顶点工厂类型。默认只开「用于静态网格」= 10 个着色器；全打开 = 186 个。
- 更糟的是父子关系：**父材质开一个标记，等于给它每一个子实例都加一整组**。《堡垒之夜》的父材质一个 section 累积了 **282+ 个静态开关**，材质大到打不开、一打开就卡死。

**三、工程侧具体省了多少（UE 5.8，多数默认启用）**

| 动作 | 收益 |
| --- | --- |
| 顶点着色器与像素着色器拆独立常量缓冲区 → 顶点着色器跨材质去重 | −331,575 个 shader，省 1826 MB |
| 只编 Skin Cache、扔掉 GPU Skin 顶点工厂（`r.SkinCache.CompileShaders`） | **省 2500 MB，本次最大单项**（前提是项目真全用 Skin Cache） |
| ISM 统一走 local 顶点工厂、从 GPU Scene 读实例数据 | 省约 400 MB |
| 先翻译材质再决定编哪些着色器（修「空材质凭空加 100 个 shader」） | 默认行为，`r.Material.UseShaderCompilationParameters` |
| 阴影深度 3 种排列 / Slate 8 种 / 半透明 base pass 2 种 → 改动态分支 | 各约 200 MB；Slate 走 `slate.MaterialShaderMode` 要权衡性能 |

### 最值得记的方法论

已发布的内容**不能**直接删 flag（会让皮肤变成灰色 fallback）。正确姿势是：

1. 用引用查看器（`AssetRegistryHelpers`）递归找出父材质的所有实例
2. 每个 flag 写一个 Python 函数，判断「这个实例到底需不需要它」
3. 输出 CSV，再在**材质实例级**覆盖（UE 5.8 新增 `UnrealMaterialEditingLibrary.set_base_material_usage` 支持实例）

分支策略也很老练：**只覆盖 true 的活放在 release 分支**（零风险，本来就该是 true）；**父材质关 flag 的活放在 main 分支**（离发布远，给 QA 足够测试时间）。

另外一条新规矩值得抄进团队规范：**静态开关只在两种情况下用**——① 材质函数含纹理采样（低端硬件采样器数量有限）② 数学很重且不是所有实例都会用到。其余一律用普通 `if` 语句 + 枚举（enum）。

> 一句话总结：着色器卡顿的本质往往不是「PSO 没预热」，而是**内容资产设计让排列数量失控**。工程侧优化只能砍幂，管住 usage flag 的传播才是砍底数。

## 2. Unity 6 用 GraphicsStateCollection 做着色器预热

### 出处

- **原文标题**：GraphicsStateCollection を使ったシェーダーウォームアップについて
- **作者**：天野拓郎，株式会社 CyberAgent **SGE コア技術本部** 项目支持组（专门给公司内部项目做性能调优、故障调查、设计支持）
- **链接**：[blog.sge-coretech.com](https://blog.sge-coretech.com/entry/2026/07/07/180723)，2026-07-07
- **类型**：一线工程博客（真实生产项目踩坑记录，含完整可运行代码）
- **语言**：日文

### 为什么值得读

着色器编译卡顿（shader compile stutter）是移动端客户端面试的高频题，但大部分资料停在「用 ShaderVariantCollection 预热一下」这个层面，而这篇是从**真的上线过的项目**里总结出来的坑，还带着完整代码。

### 关键技术点

**一、卡顿的两段来源**

- Main Thread：`Shader.CreateGPUProgram`（SPIR-V / MSL 层的变体编译）
- Render Thread：PSO 生成（iOS/Metal 上是 `GpuProgramMetal.GetCachedPipeline`，Android/Vulkan 上是 `CreateGraphicsPipelineImpl`）

Metal 和 Vulkan 上 PSO 生成成本很大，首次绘制会有几毫秒到几十毫秒的卡顿。

**二、SVC 和 GSC 的本质区别**（这个区分很多人答不上来）

`ShaderVariantCollection` 只管「编哪些变体」，**不管渲染状态**（顶点布局、RenderTarget 附件、混合、深度模板等），所以只能到字节码层；真正绘制时驱动还要重新生成 PSO，卡顿依旧。

`GraphicsStateCollection` 存的是「变体 × 渲染状态」的组合，可以直接生成 PSO，是 D3D12 / Metal / Vulkan 时代 SVC 的替代品。

**三、两阶段流程**

- 收集：`BeginTrace()` → 跑一遍收集场景 → `EndTrace()` → `SaveToFile()`
- 预热：`WarmUpProgressively(4, handle)` **分帧**编译（不要一把 `WarmUp()`，会瞬间 spike）
- 细节：`isWarmedUp` 在出错时可能永不置位，要自己累加计数兜底，否则死循环

**四、三个实战坑（全文精华）**

- **AssetBundle 重复打包**：同一个 shader 被打进多个 bundle 时，Unity 会生成**多个 shader 实例**；GSC 只预热了其中一个，另一个照样卡。**这个问题只在 iOS/Metal 复现，Vulkan 不复现**（两边 PSO 缓存管理机制不同）。解法：把 shader 收进单独的 `shader-bundle`，或按 bundle 各备一份 GSC。
- **Metal 的 SubPass（Native Render Pass）里绘制的 shader 预热不生效**，Unity 6000.3 无解，只能回避或改在加载画面里预渲染。注意 `RenderGraph.nativeRenderPassesEnabled` 在 6000.5 之后是强制开启的。
- **Shader Stripping 把变体编没了** → 预热时报 `variant not found`；或者跨平台搬运 GSC 触发 `GraphicsDeviceType / RuntimePlatform / QualityLevel mismatch` 警告。

还有一条容易忽略：GSC 里的 GraphicsState 是**按图形 API 生成**的，必须在目标设备的构建上收集，不能用 Editor 的。

> 一句话总结：Unity 6 把「预热」从字节码级推到了 PSO 级，但它**管不到资产打包造成的重复实例**——预热清单和包体设计必须一起管。

## 3. Is Complex Agentic Memory Always Needed? Naive RAG Is Stronger Than We Thought

### 出处

- **论文**：[arXiv:2610.30755](https://arxiv.org/abs/2610.30755)，2026-10-22 提交
- **作者**：Zhengye Bao, Shengtao Zhang, Haokai Zhang, Shiqi Lou, Muning Wen, Minnan Luo 等
- **篇幅**：62 页（含附录）
- **类型**：arXiv 预印本（未见同行评审），但实验设计干净、baseline 明确
- **语言**：英文

### 结论

用一个朴素到不好意思的基线 **Raw-RAG**（原始对话历史做 dense retrieval + rerank，直接喂给 reader），在 **7 个 benchmark-model 设置里 6 个排第一**，超过最强的 agentic memory 系统 **0.13 ~ 5.53 分**（覆盖 LoCoMo、LongMemEval、MEME、MemoryAgentBench）。

### 为什么它能赢

记忆系统做变换（总结、结构化、图化、学习检索策略）时，存下来的是「提炼过的结论」，但丢掉了**推导结论需要的中间关系和依赖路径**。原始证据的覆盖率更高，能补回利用率上的劣势。

最狠的一个实验：即使把变换后记忆库的访问全部给满，**精度仍然赶不上直接看原始证据**。

### 值得借鉴的工程原则

- 上复杂记忆结构之前，**先把 raw-history 检索做成基线**，之后每加一档复杂度都跟基线打一次
- 「看起来很高级」不等于更强；在长对话理解这个具体任务上，复杂度带来的收益可能为负

> 一句话总结：这篇是「过度设计」的反面教材，而且它是用实验，不是用观点。

## 4-7. 选读

**4. Why Bother Me Again? Benchmarking Personal Agent Memory for Interaction Preferences**
[arXiv:2610.30485](https://arxiv.org/abs/2610.30485) · 97 页 · MemPABench

测的是「agent 该不该记住你不想被反复追问」。结论扎人：检索式记忆（Mem0 / MemOS / 简单 RAG）**打不过 No Memory**；File-based 记忆能提精度，但会把偏好用到不相关的场景里。价值在于它量化了「记住了 ≠ 用对了」。

**5. The Horizon Gap: Planning, Memory, Execution, Training, and Evaluation for Long-Horizon LLM Agents**
[arXiv:2608.06663](https://arxiv.org/abs/2608.06663) · 39 页 · 综述（系统收割 1547 篇 2024–2026 的论文）

别通读。只取它最有用的一个贡献：把三件天天被混为一谈的事拆开了——**long-horizon（任务属性：要多少步）、long-context（模型属性：token 容量）、long-term memory（系统属性：跨步/跨会话持久化）**。这三个概念分清楚，讨论「agent 怎么处理长任务」才不至于鸡同鸭讲。

**6. DuoCook: An Overcooked-Inspired Benchmark for Visual Planning and Coordination**
[arXiv:2610.31511](https://arxiv.org/abs/2610.31511)

**用 Unreal Engine 搭的 benchmark**（地图还是 coding agent 生成的），让视觉语言模型同时控制两个玩家做协作烹饪。最值得记的不是 26.2% 的订单完成率，而是它**怎么把「游戏」变成可评测的 agent 环境**：prop legend 和锅具数量指示器提供视觉线索、格子化目标点保证空间 grounding、连 API 花费都纳入指标。

**7. Can LLMs Improve Their Own Harness? A Controlled Study on ARC-AGI-3**
[arXiv:2610.30499](https://arxiv.org/abs/2610.30499)

概念最值钱：**harness**——编排模型调用的那层符号程序，负责感知、记忆、工具、恢复、推理分配。实验结论偏负面（两次自我修订平均只涨 2.80 分，而且开发集收益会高估留出集），但「模型能力 vs harness 能力怎么分离」这个问题本身，是任何 agent 工程都绕不开的。
