## 1. Generating a State Object Database for Advanced Shader Delivery（UE 5.8 官方文档）

### 出处

- **原文标题**：Generating a State Object Database for Advanced Shader Delivery
- **作者 / 机构**：Epic Games，Unreal Engine 5.8 Documentation
- **链接**：[dev.epicgames.com](https://dev.epicgames.com/documentation/unreal-engine/generating-a-state-object-database-for-advanced-shader-delivery)
- **首发**：2026（UE 5.8 文档）
- **类型**：官方文档（一手，可当实现规范用）
- **语言**：英文

### 为什么值得读

上一期讲了两件事：堡垒之夜怎么把着色器排列砍到 68%，以及 Unity 6 怎么用 GraphicsStateCollection 把预热从字节码级推到 PSO 级。这两条线都指向同一个敌人——**PSO 在运行时生成会卡**。

这篇是这条线的第三个环节，也是 UE 侧目前最激进的一步：**干脆别在玩家机器上编译了**。DirectX Advanced Shader Delivery（ASD）把 PSO 编译搬到「商店按 GPU 家族 + 驱动预先算好」，随游戏一起下发。

两个文件类型，记住就行：

| 文件 | 是什么 | 谁生成 |
| --- | --- | --- |
| **SODB**（`.sodb`） | GPU 无关的「本工程有哪些着色器和 PSO」清单 | **你**，用 ASDTool 从 cooked build 生成 |
| **PSDB**（`.psdb`） | 把 SODB 针对某个 GPU 家族 + 驱动编译的成品 | **商店**，按 GPU 分发 |

### 几个必须知道的边界（文档里写得很清楚，别踩）

- 只适用 **Windows D3D12 + Shader Model 6**（`PCD3D_SM6`）；**不支持光追 PSO**
- **要和 PSO precaching、bundled PSO cache 并存使用，它不替代任何东西**——文档明确建议保留 precaching（避免从磁盘加载预编译着色器带来的小卡顿，也覆盖 PSDB 里缺的那些 PSO）
- **不是所有玩家都能吃到**：商店只为受支持的 GPU 家族和有限的近期驱动提供 PSDB。老显卡、老驱动照旧运行时编译
- ASD Tool 是引擎里的程序目标（`Engine/Source/Programs/Windows/ASDTool`），**没有预编译二进制，要源码引擎自己编**

### 实用细节

- 图形 PSO 只能从 PSO cache 收集（`-BundleDir` 读 `.upipelinecache`），compute 可以用 `-AllCompute` 收全部 → **你的 PSO cache 质量直接决定图形部分的覆盖率**，这一条把上一期的「资产治理」和这一期的「商店预编译」串起来了
- `-Engine` 参数只写主次版本号（如 `UnrealEngine5.8`），多写驱动可能不认
- 本地验证三连：`compilepsdbs -LocalAdapter` → `registerpsdbs -ExePath` → 用 [D3D12CacheListener](https://github.com/jenatali/D3D12CacheListener) 听 D3D12 的 ETW 事件看命中率。不命中时它会告诉你**是哪个字段没对上**（应用名 / 版本 / 可执行文件名 / 引擎名 / 引擎版本）
- 着色器没改就不用重新生成 SODB

> 一句话总结：PSO 卡顿的治理从「预编译」走向了「分发」——但前提是你先把 PSO cache 收集干净，否则商店替你编的也只是你上交的那部分。

## 2. Fix Your Timestep!（Glenn Fiedler，2004）

### 出处

- **原文标题**：Fix Your Timestep!
- **作者**：Glenn Fiedler（Gaffer On Games，Game Physics 系列）
- **链接**：[gafferongames.com/post/fix_your_timestep](https://gafferongames.com/post/fix_your_timestep/)
- **首发**：**2004-06-10**（原文标注 9 min read，实际精读 20 分钟左右）
- **类型**：行业经典博客（一手，作者是网络物理同步方向的长期实践者）
- **语言**：英文

### 为什么值得读

我这段时间在写一个游戏时钟子系统，最难的不是「怎么把时间拆成秒」，而是**谁来决定一帧推进多少**。这篇 2004 年的文章把这问题拆得极其干净：

**四种做法，一条演化线**

1. **固定 dt**：`while(!quit){ integrate(dt); render(); }` —— 理想情况完美，但你的 dt 得和刷新率对上，且机器要跑得动
2. **可变 dt**：把上一帧耗时当 dt 喂进去 —— 听起来对，实际是灾难：**物理行为本身依赖 dt 的大小**。轻则手感随帧率变，重则弹簧炸到无穷、高速物体穿墙、角色掉进地板
3. **半固定 dt**：`deltaTime = min(frameTime, dt)` 把大步切小 —— 有了上界，但会一帧多步 + 一个余量步
4. **累加器（accumulator）**：换视角——**渲染负责「产生时间」，模拟按固定 dt「消费时间」**，剩下的余量藏在累加器里留给下一帧

```c
accumulator += frameTime;
while (accumulator >= dt) {
    previousState = currentState;
    integrate(currentState, t, dt);
    t += dt;
    accumulator -= dt;
}
const double alpha = accumulator / dt;
State state = currentState * alpha + previousState * (1 - alpha);
render(state);
```

最后那几行是精华：**用余量做渲染插值**，否则你渲染的是「略微落后于真实时间」的旧状态，看起来就是那种说不清但很难受的抖动。

### 它提到的那个词，正好是我代码里的病

**spiral of death（死亡螺旋）**：模拟追不上要模拟的时间 → 下一帧要模拟更多 → 更追不上 → 无限循环。

文章给两个解法：**留 headroom**（模拟 X 秒比真实 X 秒快得多，才能追上临时尖峰），或者**给每帧最大步数封顶**（代价是重负载时画面变慢，但总好过卡死）。

> ⚠️ 我自己的 Tick 里的 `while` 循环和 `ChangeTimeScale` **都没有上限**——这就是标准的死亡螺旋入口。这篇给了我改它的依据，不是「据说要限一下」，而是「不限的失败模式叫这个，代价是这个」。

### 放到今天还成立吗？

**思想成立，代码别照抄。**

- **成立的部分**：累加器 + 插值 + 步数封顶，这套在任何需要「模拟与渲染解耦」的场合都成立——帧同步、确定性回放、独立服务器 tick 都吃这个
- **已被取代的部分**：现代引擎把这段封装掉了。Unity 有 `FixedUpdate` 和 `Time.maximumDeltaTime`，UE 有固定 tick 与 substepping 配置——你不需要自己写那个 `while(!quit)` 主循环
- **没被取代的部分**：如果你在写**引擎之上的模拟层**（比如游戏内时钟、回合结算、状态推进），累加器这件事还是得自己做，而且会踩一模一样的坑

> 一句话总结：渲染产生时间、模拟消费时间——想清楚这句话，帧率高低就不再是模拟正确性的变量。

## 3. UnityBench-Mini3D: Evaluating LLM Agents for 3D Game Development in Unity

### 出处

- **论文**：[arXiv:2610.35980](https://arxiv.org/abs/2610.35980)
- **作者**：Yijun Zhou、Minghao Shao、Ke Zhang、Renkai Yuan、Hongbo Yuan、Jie Feng 等
- **首发**：2026-10-26
- **类型**：arXiv 预印本（未见同行评审，但实验规模和评测设计值得看）
- **语言**：英文

### 为什么值得读

因为它回答了一个我很好奇的问题：**让 AI 写游戏，到底难在哪，怎么量化？**

现有基准大多只测代码能不能跑（比如 Godot 生态的），或者依赖 LLM 判卷、只看任务级结果。这篇的做法不一样：

- **77 个项目级 Unity 任务**，按 7 个专家定义的技能类组织（不是按教程或游戏类型分），三档难度
- 每个任务 = **一整个 Unity 工程** + 自然语言需求
- 评测用 **1178 条人工写的里程碑测试**，跑在引擎里，检查三件事：**场景结构、组件配置、运行时行为**
- 因为测试是确定性的，所以能给**部分分**、能定位失败点、能区分「实现了一半」和「做完了」——**完全不用 LLM 判卷**

结论也挺诚实：21 个模型 × 9 种 harness，简单任务平均通过率 80.9%，**困难任务掉到 35.2%**，总体 57.7%。

### 为什么它比一个排行榜更有价值

作者的核心洞察是：**游戏开发的正确性不只取决于源码**——还取决于引擎 API 怎么用、场景的序列化状态是什么、运行时表现如何。所以：

- 只读代码的评测，看不出一句「脚本写对了但组件没挂上」
- 只跑起来截图，也说不清是场景搭错还是脚本错

「引擎内跑里程碑测试」这个设计，我直接就想搬到自己项目里：**把「我觉得这样算对」变成可执行断言**。

> 一句话总结：评测游戏 AI 的难点不在模型，在**怎么把「对的游戏」写成能被机器验证的断言**。

## 4-7. 选读

**4. Gym-Anything-RT: Scaling Real-Time Environments for Vision-Language Agents**
[arXiv:2610.37567](https://arxiv.org/abs/2610.37567) · 2026-10-27

给「实时交互」专门造了 100 个视觉小游戏，并且能**开关实时性**做对照。数字很扎：GPT-6 Astra（xHigh）实时模式下通过率 **9.0%**，把环境暂停后升到 **75.0%**。还有个有意思的现象——能力强的 agent 会主动写代码去**绕过实时感知和操作**。对做「Agent 驱动游戏」的人来说，这条结论比任何 demo 都重要：**实时性是独立的一维能力，不是推理能力的副产品。**

**5. TaskFrame: Connecting Task-Level Planning with Frame-Level Control for Game Agents**
[arXiv:2610.40276](https://arxiv.org/abs/2610.40276) · 2026-10-29

分层：视觉语言模型做任务级规划（拆成原子指令），因果 Transformer 控制器输出键鼠动作和镜头移动。设计上的关键论点——**高层推理和低延迟控制在算力画像上差别巨大，很难塞进一个模型**。另外它把「目标 token 的隐状态」当连续目标向量缓存复用，省掉每步重复计算，工程上挺巧。

**6. Data-Oriented Design and C++（Mike Acton，CppCon 2014 主题演讲）**
[CppCon 2014 / isocpp 记录](https://isocpp.org/blog/2015/01/cppcon-2014-data-oriented-design-and-c-mike-acton)

旧料，但它是**数据布局优先于抽象**这个思路的源头之一。为什么推：C++ 面试问到第四层，考的就是「你为什么这么摆内存」。看它比背八股管用——它给的是判断标准，不是结论。放今天仍成立，唯一要打补丁的是：现代编译器、SoA 库和 ECS 框架把这套实践成本降了很多，不必每一步都手写裸数组。

**7. How Humans Learn Unfamiliar Worlds: A Think-Aloud Dataset on ARC-AGI-3**
[arXiv:2610.34523](https://arxiv.org/abs/2610.34523) · 2026-10-25

记录人类在陌生环境里边玩边说话（144 条轨迹 / 64 人 / 25 个游戏），再和 LLM agent 对照。最有用的一条数据：**成功的真人轨迹里，定性表征占 50.0%，成功的 LLM 轨迹只有 14.3%**——人靠「这像什么」类比推理，模型更依赖具体假设检验。数据集带标注，可以当评测设计的参考。
